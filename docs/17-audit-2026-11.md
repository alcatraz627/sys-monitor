# Audit, November 2026

<!-- sessions: audit-widgt-7e@2026-11-12 -->

An audit of the app after several months of daily use, prompted by three
complaints: the numbers feel off, the panel does not say where to look when
something is hogging the machine, and the panel feels clunky. It also covers the
first build of a Notification Centre widget.

Machine: Apple M5 Pro, 18 cores, 64 GB, macOS 27.2. Branch `fix/accuracy-and-fit`.

## What was wrong, and what was done

| # | Finding | Evidence | State |
|---|---|---|---|
| 1 | Every process showed about 1/42 of its real CPU. | The kernel reports per-process CPU time in mach ticks, 125/3 ns each on Apple Silicon, and `ProcessSampler` read them as nanoseconds. A busy loop that used 2.00 s of CPU was seen as 0.048 s. | Fixed in `1fb7121`. A self-test burns a known amount of CPU and checks the reading; with the fix reverted it fails with "sampler saw 2%". |
| 2 | System processes were missing from the list. | `proc_pidinfo` is refused for WindowServer, launchd and about 300 others. At the time of the audit WindowServer and kernel_task were the second and third largest CPU users and neither could be named. | Fixed in `1fb7121`. One `/bin/ps` call per process sweep supplies them. Measured at 30 ms a call, and it only runs while the panel is open. |
| 3 | A high reading did not say who caused it. | The CPU and MEM headers carried a number and a colour. Finding the cause meant choosing the matching sort in the process list, and the saved sort was memory. | Fixed in `54805df`. Each header names its top two, and a click sorts the list by that metric. Memory is counted per app, helpers included. |
| 4 | The panel changed state by replacing things. | Only the per-core bars animated. Figures snapped, rows jumped rank, sections appeared, and every open blanked the process list to "Measuring processes" for about 300 ms. | Changed in `54805df`. Not yet confirmed by eye; motion cannot be read from a still render. |
| 5 | A pin outlived its process. | Pins are stored by pid. Two pids were in the saved settings from processes long gone, ready to pin whatever reused the number. | Fixed in `a7203ca`. Not yet exercised in the running app. |

The old comment that explained why an "unaccounted CPU" row had been dropped
described a symptom of finding 1: summed process CPU fell about two cores short
of the machine total because every process was under-reported.

## Checked and correct

- Overall CPU and per-core CPU use the same kernel source as `top`.
- Memory used is app + wired + compressed, which is Activity Monitor's figure.
  From `vm_stat` at the time: 25.35 GiB computed by hand against 25.3 GiB shown.
- Swap matched `sysctl vm.swapusage` to two decimals.
- The app's own cost over 31 days of uptime averaged 0.64% of one core.

## Open

- **System process memory is resident size, not footprint.** `ps` cannot give
  the footprint. WindowServer read 338 MB where Activity Monitor shows 1.4 GB.
  Their disk, network and power are unknown and show a dash.
- **kernel_task is not listed.** `ps` does not report it.
- **Network may count tunnel traffic twice.** Every interface but loopback is
  summed, including 18 `utun` tunnels and the bridge. With a VPN up, the same
  bytes cross the tunnel and the physical interface. Not measured: no tunnel
  carried traffic during the audit.
- **Storage shows free space only.** Nothing points at what is using the disk.
  See [16-disk-cleanup-note.md](16-disk-cleanup-note.md).
- **Free space may differ from Finder's**, which counts purgeable space as
  available. Not measured.
- **Stale saved settings.** A zoom of 130% is still stored though zoom is off,
  and a panel height of 969 against a stated cap of 900.
- **The probe renders one appearance.** Dark mode was not read for the new
  culprit lines.

## The widget

A WidgetKit extension now builds from `Widget/` with the command line tools
alone, compiled from the app's own sampler sources, and `./build.sh --install`
places it in the installed app. It shows memory, storage and battery in small
and medium sizes. macOS refreshes a widget every few minutes at best, so it
carries only figures that stay true that long.

State on 2026-11-12: macOS registers the extension (`pluginkit -m -i
dev.sys-monitor.menubar.widget` lists it), but the widget host logs "purging
instead because we shouldn't cache it" each time. Whether it still appears in
the widget gallery has not been checked. If it does not, the likely cause is
the ad-hoc signature, and the next step is to sign the extension with a real
certificate.

Not built yet: the top-process line in the widget, which needs data from the
app because a sandboxed widget cannot list processes, and the optional live
desktop panel.
